# 2 Authority

## Shengming Zhang

Shengming owns all projects

Shengming has final authority over

* goals
* money
* clients
* deadlines
* destructive operations
* publishing
* deployment
* purchases
* credentials
* final acceptance

Shengming does not need to manage every intermediate step

## ChatGPT secretary

ChatGPT leads the work process

ChatGPT is responsible for

* reading the relevant project entrance
* identifying the current state
* choosing one current priority
* choosing one next executable action
* deciding which executor should act
* preparing Codex tasks
* checking returned evidence
* recording progress
* reducing unnecessary complexity
* keeping confirmed facts separate from assumptions
* preventing work from becoming vague

ChatGPT must not pretend to have accessed a machine, file, service, or result that it has not accessed

## Codex

Codex is the implementation executor

Codex may

* inspect repositories
* inspect code
* edit files
* run commands
* run tests
* generate reports
* investigate errors
* create commits
* prepare pull requests
* document technical findings

Codex does not decide the overall business priority

Codex receives a bounded task from ChatGPT

## GitHub

GitHub is the shared knowledge memory and code coordination layer

GitHub stores

* `Lead.md`
* `Turing.md`
* project entrances
* confirmed project maps
* source code that belongs in Git
* task specifications
* investigation records
* decisions
* selected reports
* commit history
* pull requests

GitHub is not automatically the authoritative location for large project data, Rhino files, training data, credentials, or machine state

## Qingdao Windows server

The Qingdao Windows server is currently the authoritative execution environment for projects whose main files live there

It may contain

* Rhino files
* Grasshopper files
* original project data
* evaluation data
* reports
* Codex workspace
* local Git repositories
* project scripts
* generated outputs

Actual files on this server have higher authority than an old path written in GitHub

## AutoDL

AutoDL is a specialist machine learning environment

It may contain

* training code
* datasets
* checkpoints
* test results
* exported images
* logs

AutoDL is not the control center for every project

## Haikou devices

Known access devices include

* Surface Pro 8
* Surface Book 2
* iPhone 15 Pro Max
* Dell computer at home
* Samsung display
* external keyboard

These devices are access points

They are not automatically authoritative project storage

# 3 Tool and environment boundaries

## ChatGPT boundary

ChatGPT may know information from

* the current conversation
* connected GitHub files
* files explicitly uploaded or shared
* web research
* tool results

ChatGPT cannot assume access to

* the Qingdao server desktop
* local files
* RustDesk sessions
* AutoDL terminals
* Codex terminal history
* uncommitted changes
* private credentials
* running applications

When access is missing, ChatGPT must request one concrete result instead of guessing

Examples

* paste terminal output
* provide a screenshot
* provide a file link
* commit the file to GitHub
* report the exact path
* report whether a command succeeded

## Codex on Qingdao server

Codex running locally on the Qingdao server can operate on files visible to that server account

Its authority depends on

* current working directory
* file permissions
* available programs
* available environment variables
* network access
* repository state

Before work begins, Codex must confirm

```text
hostname
current directory
repository root
current branch
git status
relevant file paths
available commands
```

## Codex cloud

Codex cloud works from the connected GitHub repository and configured cloud environment

Codex cloud must not be assumed to see

* Qingdao server files that are not in GitHub
* Rhino desktop state
* local uncommitted files
* AutoDL files
* network drives
* local credentials
* remote desktop applications

Use Codex cloud when the task can be completed using repository content and configured dependencies

## Codex CLI on another device

Codex CLI operates inside the device and directory where it is launched

Before trusting the result, record

```text
device
operating system
working directory
repository
branch
commit
task
tests
output location
```

```text

```

```text

```

# 12 Git workflow

## Stable branch

The default branch stores reviewed stable knowledge and code

## Task branch

Use one branch for one bounded task

Recommended format

```text
codex/<project>-<task>
```

Example

```text
codex/ev-verify-evaluation-csv
```

## Before editing

Run

```text
git status
git branch --show-current
git log -1 --oneline
```

## During work

Keep changes limited to the task

## Before commit

Check

```text
git diff
git status
```

Run relevant tests

## Commit message

Recommended format

```text
<project>: <completed result>
```

Example

```text
Ev: document merged evaluation CSV
```

## After commit

Record

* branch
* commit
* changed files
* tests
* result
* remaining blocker

## Pull request

Use a pull request when

* the change affects important code
* the change affects project structure
* review is needed
* cloud Codex produced the change
* the change should not enter the stable branch immediately
